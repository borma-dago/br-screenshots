#### Corrections this collection makes to statements on the record

- **"Akeneo moved from rows to `raw_values` JSONB in 3.0"** (Catalogue Next Steps v7, step 2) is **wrong on both halves**. Measured across branches: `1.7`'s `Product.orm.yml` (2,469 B) has a `values` oneToMany to `ProductValueInterface` and no `raw_values`; `2.0`'s `AbstractProduct.orm.yml` (3,023 B) has `rawValues / raw_values` and no `values` association, and `ProductValue.orm.yml` is absent from the 2.0 tree — reconfirmed at tag `v2.0.0`. **The change is 1.7 → 2.0, not 3.0.** The column type is Doctrine `native_json` (2.0–3.0) and `json` on master — **not `jsonb`**. `raw_values` appears 0 times in CHANGELOG-1.7, -2.0, -2.3 and -3.0.
- **#10778 V4 cites "Akeneo `sort_order`" as evidence that every surveyed system hand-orders.** Akeneo actually ships **both mechanisms behind a per-attribute toggle**. The UI query branches on `auto_option_sorting`, which defaults to `false` (`SqlSearchAttributeOptions.php:139-147`): when true it orders by the *translated label* (`orderBy('v.value')`), when false by `sortOrder` then `code` (`InternalApi/AttributeOptionSearchableRepository.php:60-72`). Akeneo's help centre states both in its own words: *"Options can be **automatically sorted by alphabetical order** using the toggle button `Sort automatically options by alphabetical order`… If you want to define your own sort, you **can manually drag and drop option rows to reorder options.**"* So the one PIM V4 leans on hardest offers alphabetical ordering as a first-class alternative — a **second independent route** for the partial supersession recorded in §7.
- **An unresolved contradiction between two official copies of PerBPOM 31/2018**, recorded rather than resolved: Pasal 26(3)'s internal cross-reference reads *"sebagaimana dimaksud pada **ayat (2)**"* in the BPK copy and *"…pada **ayat (3)**"* in the Berita Negara copy. Separately, **Pasal 26 has no ayat (4)** in either copy (it runs (1),(2),(3),(5),(6)), confirmed in two extraction modes. Neither affects the unit rule quoted in §6.3.
- **Corrections the Shopify / Square / eBay collection makes to statements on the record:**
  - **"Shopify keeps weight on the variant, outside the attribute system"** (Catalogue Next Steps v7, card A1) is wrong on the first half. Measured on three API versions (`2025-10`, `2026-01`, `2026-07`) through the public Admin-GraphQL proxy: `ProductVariant` has **41 fields and none whose name contains "weight"**. Weight is at `ProductVariant.inventoryItem.measurement.weight`, and it is a **`{value, unit}` pair** — retrieved live: `{"value":0.0,"unit":"KILOGRAMS"}`. The second half stands: it is outside the attribute/metafield system. *The A4-relevant part is the shape*: Shopify's own weight is quantity form (iii), amount plus unit, not a label. (Card A1 is ATTR-DEF's; flagged, not decided here.)
  - **Square's "10 visible + 10 hidden" cap has no per-object reading in any artifact.** One vendor page states it twice with **two different scopes** — *"Each Square account can have up to 10 seller-visible and 10 seller-hidden custom attributes"* and *"An application can create up to 10 seller-visible custom attribute definitions defined by a `CatalogCustomAttributeDefinition` object"* — and the OpenAPI spec is silent (`10 seller` → 0 hits in 3,273,134 B). #11031 already records a scope contradiction here (§4 row 16); this collection confirms it is a contradiction **inside a single vendor page**, and that neither reading is "per object". Cards A0/A1 use the figure; they should carry the scope hedge.
  - **eBay's "inheritance override model" is a retired mechanism.** The page carrying that rationale is `GetCategoryFeatures` (Trading API v1423), whose own banner reads: *"This call has been deprecated and will be decommissioned on May 4th, 2026. Users are recommended to migrate to the Metadata API…"* — a date already past at this snapshot. The Taxonomy API's `fetchItemAspects`/`getItemAspectsForCategory` return a **full per-category aspect list, not an override delta**. Card B4 and the step-1 fork both lean on that model as the only fully worked inheritance reference; TREE owns those, so this is flagged, not decided.
  - **eBay's aspect values can be conditional on another aspect's value** — `AspectValue.valueConstraints[]` carries `applicableForLocalizedAspectName` + `applicableForLocalizedAspectValues`, with eBay's own worked example: *"A shirt is available in three sizes and three colors, but only the Small and Medium sizes come in Green… Only when the Size aspect value is Small or Medium, can the Color aspect value of Green be selected by the seller."* That capability is expressible only over value **rows**, and it is a live counter-case to the idea that a closed list is just a string set. Not proposed for us; recorded because it is the strongest thing rows buy that this brief does not otherwise cost in.
