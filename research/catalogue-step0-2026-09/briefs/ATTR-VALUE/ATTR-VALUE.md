## A3 · Is "Rasa" one attribute type shared by every category that wants it, or does each category define its own?

### 1 · Options

As the card states them, plus one extension with a stated reason.

- **(a) One global type; categories subscribe.** One definition object; a join table links it to many categories. Card's claim: one search filter across categories, values survive a category move, one list to curate.
- **(b) Each category owns its own copy.** The definition is scoped to the node; the "same" attribute in two categories is two objects. Card's claim: each category curates its own, no cross-category filter, a move loses values.
- **(c) Shared type, per-category value list.** One `Rasa`, but noodle flavours and snack flavours are different lists.
- **(a′) One global type, subscribed, with a per-membership display name.** *Added, with reason:* this is a real shipped mechanism (Shopify's `extended` attributes — 106 base attributes, 316 extended names, 2,891 of 93,007 edges, every one reusing the base attribute's GID and its single value list; `corpus-analysis/shopify_attr_reuse.out` §4). It is not a variant of (c) — the value list is not subsetted, only the label changes — and it answers the card's motivating case at the cost of one nullable column. Excluding it would have hidden the cheapest answer.
- **(d) No category-scoped attribute concept at all.** Not an option for us (Lock 1 makes the category the type), but three platforms sit here and dropping them would bias the tally.

**Framing note that governs every row below:** on most platforms the attribute-owning object is **not the browse category**. It is Magento's `eav_attribute_set`, Akeneo's `Family`, commercetools'/Amazon's/Walmart's `ProductType`, Salesforce's `Product` object type plus category-attached groups. Only **Shopify, eBay, Shopee and Tokopedia** merge the two — and Lock 1 merges them for us. So (a)-vs-(b) is orthogonal to whether the subscriber is the browse tree, and a platform can be (a) while keeping the browse category entirely out of it (Magento: *"The browse category plays no part in any schema table"*, #11082 §3.1; Akeneo: `grep -c attributes Category.orm.yml` = **0**, #11069 §1.8).

**The (c) column is empty, and that is the finding.** The closest anything comes is commercetools, which is (c) on the *values* and (b) on the *object*: *"the enum values can be different for each ProductType"* with the type forced to match (#11081 §1.4). No platform ships a shared definition with a per-category value list.

**The counter-finding that matters most, and it comes from the biggest (a) platform.** Shopify does not reuse one `Flavor` across domains — it mints more global types. Its own record: *"Attacking that pattern with the vendor's synonyms… returns **30 distinct handles**, of which **11 are flavour/taste-family** — and **each is a separate base attribute with its own value list.** Shopify does **not** reuse one `flavor`"* (#11011 §3). I re-measured that in the corpus and got the same shape: nine attribute names containing "flavo(u)r", `Flavor` on 293 categories with 30 values, `Pet food flavor` 43 values / 54 categories, `Baby food flavor` 41 / 4, `E-liquid flavor` 22 / 10, and five more on one category each (`corpus-analysis/shopify_attr_reuse.out` §3). Same for size: the matrix records *"300 of 8,240 definitions match size, volume, weight or capacity — and every one is category-specific"* (`catalogue-decision-matrix-2026-09-16.txt:368`); my regex is slightly wider and returns **329**, of which **219** are on ≤1 category.

So (a)'s headline benefit — one filter across categories — **does not materialise for flavour or size even on the platform that invented the mechanism.** It materialises for `Color` (11,730 edges), `Pattern` (11,686) and `Material` (4,546).

### 3 · Why

Stated rationale where a primary artifact in the record gives one; otherwise the constraint, labelled inference.

- **WooCommerce — the only explicit design rationale for globality in the thirteen records.** Vendor: *"Attributes can be defined globally, **so they’re easy to update across the entire store**, and available to be used on any product, or; … defined individually, at the product level, and they will only exist for that single product."* (`11080.md:338`, `:629`; the record uses a typographic apostrophe and this brief now reproduces it — finding R1-24, it is what defeats a plain `grep -F`)
- **commercetools — the only explicit argument for per-type scoping.** Vendor: a `T-Shirt` type has `Color` *"an enum with options like Red, Green, and Blue"*, a `Jeans` type has `Color` *"an enum with a different set of options like Blue, Black, and Grey"*, and: *"**You wouldn't ask for the `Neckline` of a pair of jeans, would you? By defining appropriate Attribute types for each Product Type, you prevent irrelevant or nonsensical data from being entered, maintaining data integrity and simplifying product management.**"* (#11081 §3)
- **Shopify — rationale for the category constraint, in its own words:** *"By default, metafield definitions apply to every resource on their owner type… However, some metafield definitions should only apply to a subset of resources"*, with the worked example *"`Shoe size` is a valid metafield for `Shoes` products but wouldn't apply to `Sweaters`."* (#11011 §1.8). No statement exists in the record explaining why the taxonomy attribute is global rather than per-node.
- **Walmart — the vendor states the consequence, not the reason:** *"Based on the chosen Product Type, attribute requirements, values, and recommendations will vary."* (#11046 §1.2)
- **Magento — Adobe states the purpose of the set, not of the sharing:** *"The attribute set determines the fields that are available during data entry, and the values that appear to the customer."* (#11082 §1.2)
- **Akeneo — the clearest stated purpose of any:** *"The family helps managing the product's completeness as you can say at the family level, which family attributes are required for the completeness calculation."* (#11069 §1.1)
- **eBay — no stated rationale.** *Inference:* eBay is a marketplace whose category tree is the seller-facing contract and whose aspect list is versioned per `(category_tree_id, category_id, marketplace)`; a globally identified aspect would have to be versioned globally across 15,111 leaves and 24+ marketplaces at once. Per-leaf materialisation lets a category's aspect set change without a global migration — the same reason the record finds that the same category id under two trees returns two different aspect lists (#11045 §1.7).
- **Amazon — no stated rationale.** *Inference:* Amazon compiles a JSON Schema per `(product type × marketplace × parentage level)` and distributes monthly deltas; a stable attribute `name` is what lets 381 legacy XPaths map onto one pointer and lets a schema be regenerated without invalidating stored values. The join being mutable (*"Attribute is deleted and no longer associated with the product type"*, 15,299 of 26,135 flavour release-note rows) is only survivable if the attribute outlives the membership.
- **Google — no stated rationale.** *Inference:* Google receives a flat feed from sellers it does not control and whose categories it does not own; a per-category schema would require every seller to resolve a taxonomy node before serialising a row.
- **Square — no stated rationale.** *Inference:* single-tenant seller tooling where the merchant authors both the categories and the attributes, and a cap of 10+10 definitions removes the problem scoping would solve.
- **Salesforce B2C — no design rationale beyond** *"to help you manage product attributes"* (#11050 §1.7). *Inference:* a single-tenant storefront platform where the merchant owns the tree, so inheritance costs nothing and saves per-node authoring.
- **Tokopedia Era B — operational statement only:** *"Use the Get Attributes to check what attributes are mandatory and pass attribute values via the Create Product…"* (#11048 §1.8).
- **Shopee — no rationale; one sentence of mechanism.** The record notes Shopee *"publishes no attribute inventory, no value inventory and no category file of any kind… There is nothing to count."* (#11047 §3)

### 4 · Our code today

Full call-site table in `design-A3.md` §0–§5. The load-bearing facts:

- **The whole set-reader is two lines**: `get_all_attributes()` → `self.product.get_product_class().attributes.all()` (`py/mono/solvent/catalogue/product_attributes.py:57-58`), used by `validate_attributes()` (`:36-52`, called at `models.py:484`) and `save()` (`:60-64`, called at `models.py:490`).
- One more hard-coded read of the *global* set: `staff_views.py:66-67` (`ProductClass.default().attributes.all()`, served at `staff_urls.py:16` behind `@cache_page(86400)` at `staff_views.py:73`). **And one read through the product's own FK**, which is not the same thing (finding R1-27): `staff_serializers.py:70-72` is `product.product_class.attributes.all()` — identical to the global set only while `productclass_rows = 1`, and the two diverge under option (b), which is exactly the distinction this section draws.
- `ProductClass.default()` is `ProductClass.objects.get()` (`models.py:88-90`) — raises the moment a second row exists. Two non-test call sites. Every option deletes it.
- **`ProductAttribute.code` has no uniqueness constraint anywhere** — no `unique=True` (`models.py:626-638`), and the only two `unique_together` in `catalogue/migrations/*` are `("product","category")` and `("attribute","product")`. A global name catalogue (#10778 C5) is currently a convention, not a constraint.
- **`required` lives on the attribute** (`models.py:655`), so it cannot differ per category today. It is already wrong: `manufacturer` is `required=True` and 59,662 products have no row.
- **Search inherits nothing — verified at the template level too.** `ProductIndex` (`search/search_indexes.py:20-75`) declares no attribute field; the category field is declared **twice** — `catalogue/search_indexes_mixins.py:22` (`AbstractCategorySearchIndexMixin`) with `prepare_category` at `:27-29` returning `[c.id for c in main_category.get_ancestors_and_self()]`, and **re-declared** by `ProductIndex` itself at `search/search_indexes.py:65` as `indexes.MultiValueField(null=True, faceted=True)`, which overrides the mixin's and is the only faceted one (finding R1-18; the bare basename was ambiguous — `solvent/search/search_indexes_mixins.py:22` is a different mixin's docstring); and the indexed document text is `product_text.txt` → `{title, title_staff, upc}` + `{category.full_name_en, full_name_id, full_code}` + `description` (`py/mono/templates/search/indexes/catalogue/{product_text,product_lite,category_lite}.txt`). **No attribute value is searchable today.** Any attribute facet is new work under **every** option.
- **The Google feed inherits nothing.** `ProductAttributes(...)` is built from availability, condition, description, link, title, price (+ sale_price, image_link) only (`third_party_api/google/content/products_api.py:214-235`). No attribute value reaches Google.
- **Frontend: the display name and the unit of every attribute live in a translation bundle**, `ts/assets/i18n/product/{id,en}.json`, read by `product-attribute-i18n.service.ts:20-35`. Adding an attribute is a frontend release. That bundle already lists `internalname`, which is not one of the five production attributes — **the registry and its display metadata have drifted at n = 5**.
- **Frontend: attribute order is a hard-coded array** (`product-attribute-ordering.service.ts:9-15`), and the hidden set is another (`product-addendum-attributes-ui.component.ts:34`).
- **A schema editor does exist — in Django admin (finding R1-11).** `ProductAttributeInline` (`solvent/catalogue/admin.py:27-29`, `model = ProductAttribute`) is mounted on `ProductClassAdmin` (`:32-34`), so attributes are authored today *under the product class*. **That inline is the single most affected surface in this card**: under (a) it becomes a membership editor on a new through-model, under (b) it re-parents to `Category`, under (c) it gains a second level. Lock condition 1's *"there is no UI for `ProductAttribute` at all today"* is true of the staff app and false of Django admin; the distinction matters because the admin inline is what staff would otherwise keep using during the migration. Two further admin surfaces read values: `AttributeInline` (`admin.py:18-19`) on `ProductAdmin` (`:46`) and `ProductAttributeValueAdmin` (`admin.py:56-57`, registered `:68`).
- **The reindex and feed fan-out is mis-ordered relative to attribute writes (finding R1-14).** `Product.save()` → `super().save()` (`models.py:489`) fires `post_save` → `receivers.py:31-41` → `index_utils.py:11-16`, which enqueues **both** the Haystack index and the Google Merchant queue; `self.attr.save()` runs at `models.py:490`, after. There is no `post_save` on `ProductAttributeValue` anywhere. So any future attribute facet or feed field is built one write stale, and a value edited through an admin inline never reindexes. This is common to all three options and is a prerequisite for the facet work A3's option (a) is supposed to unlock.
- Per option: **(a)** changes the four backend reads, moves `required` to the membership, adds `UNIQUE(code)`, and breaks the 24-hour global cache; **(b)** changes only the FK, and adds a re-point of every value row on a product category move; **(c)** adds two more tables and a two-level editor. All three force the same frontend change — the staff form must fetch attributes for the selected category and rebuild when it changes (`product-attributes-stream.service.ts:24`, `product-update-staff-form-ui.component.ts:141,147-169`).

### 6 · Cleanest / structurally correct for us

The platforms are **split**, so this is a full design pass; the sketch is `design-A3.md`. The problems each shape causes, against our real tables:

**(a) global type + membership table.** Values survive a product's category move — but if the new category does not subscribe, the row becomes an **orphan that still renders**: `validate_attributes()` iterates the category's set so it never sees it, `save()` never writes it, and `ProductDetailsSerializer` serialises `product.attribute_values.all()` unfiltered (`serializers.py:207`), which the customer product-detail endpoint `ProductFullViewSet` prefetches unfiltered and caches (`api/apiproduct/views.py:52,58-68`). The product page then shows a field its category does not have, permanently, with no code path that can clear it. Fixable at root with the move-guard lock condition 5 already asks for, plus a filtered read. Other costs: `required` must move to the membership (D17 arriving early), `UNIQUE(code)` must be added to data that has never had it, and the 24-hour global attribute cache (`staff_views.py:73`) becomes a correctness bug.

**(b) per-category copy — which is Lock 1's own sentence.** The lock comment says, verbatim: *"**Concretely:** `ProductAttribute.product_class` becomes `ProductAttribute.category`; a product sits on a node whose schema it obeys; `ProductClass` and `Product.product_class` are dropped."* (`evidence/issues/10966.md:1105`). `product_class` is a `ForeignKey` (`models.py:618-624`), so renaming it yields a **single FK to `Category`** — which is option (b), not (a). **Judgement: if A3 lands on (a) or (a′), that sentence has to be amended to a join table before the schema editor of lock condition 1 is designed.** The lock's substance — the category owns the schema — is untouched either way.
As a design, (b) is the smallest migration, needs no new table, and gives the simplest editor. Its cost is not curation, it is **mis-attribution on a move**: a value row points at a category-scoped attribute, so moving the product leaves every value referencing the old category's attribute. `unique_together("attribute","product")` does not catch it, `validate_attributes()` does not catch it, nothing does — and the value still renders. Correct handling is a re-point of every value row on every staff move. Second cost: nothing stops `flavor` being `text` on one node and `integer` on another, and Elasticsearch needs one mapping per field name, so the first divergence breaks any cross-category facet.

**(c) shared type, per-category list.** Three new tables, a two-level editor built before any attribute editor exists, and a second place a value can be wrong (offered-then-withdrawn options). It pays only if two categories genuinely need different subsets of one list — and the industry's reference taxonomy answers exactly that case with (a) plus a second type (`Flavor` and `Pet food flavor` are two definitions, not one list subsetted). Zero platforms ship pure (c).

**(a′) global type + per-membership `name_override`.** One nullable column. Gives "Rasa" on food and a different label elsewhere from one id, one value list, one filter. Working precedent at 14,606-category scale. Does **not** solve "noodle flavours ≠ snack flavours" — only a second type does.

### 3 · Why

Stated vendor rationale where a primary artifact gives one, quoted; otherwise the explaining constraint, labelled **inference**.

- **Shopify — the clearest stated "why" for a shared value row in the whole set, and it is the rename argument.** Vendor: *"Instead of using simple text for option values, you reference metaobjects that contain structured data. For example, instead of a color option with the text value "Red", you reference a metaobject that includes the color name, hex code, and taxonomy references… The metaobject's display name becomes what customers see, while the structured data powers features like improved search and marketplace integration."* And: *"you can edit the color `black` to be `graphite` and your variant values are updated anywhere that color is used."* Shopify started with strings on the product and bolted sharing back on; the reason it gives is rename plus search plus marketplace mapping.
- **Square — "why a shared option row" stated as a workflow fact.** Vendor: *"After your application creates a `CatalogItemOption`—such as "color" with predefined values—that option can be applied to define the color attribute for any new catalog items."* and the constraint that follows from it: *"because "Polo shirt" and "Club shirt" are variations of "Shirt", they're restricted to the same option values. If the seller later receives teal polo shirts, they must add "Teal" to the color option set."*
- **eBay — why free text coexists with a closed list, in the vendor's words:** *"Most categories support free-text names and values in item specifics and in variations. However, some categories require certain item specifics (e.g., Brand), and some item specifics (e.g., Color,) may require you to select a value from a predefined set."* (#11045 §3) — the governance flag's rationale, stated.
- **Akeneo — why the option is a row and the family selects it:** *"The family helps managing the product's completeness as you can say at the family level, which family attributes are required for the completeness calculation."* (#11069 §1.1) On ordering, the vendor states both mechanisms and lets the user pick: *"Options can be **automatically sorted by alphabetical order** using the toggle button… If you want to define your own sort, you **can manually drag and drop option rows to reorder options.**"*
- **Amazon — no rationale for the value shape; one staff statement acknowledging the resulting defect.** Amazon staff on the `enum`-versus-validator mismatch: *"The mismatch you've identified — where `getDefinitionsProductType` publishes human-readable display values in `enum`/`enumNames` … while the server-side validator only accepts undocumented snake_case codes … is a valid concern that warrants internal investigation."* (#10976, correction pass). *Inference for the shape itself:* Amazon compiles a schema per `(product type × marketplace × parentage level)` and distributes monthly deltas; a value carried as a scalar inside the item document survives a schema regeneration, whereas an FK into a central vocabulary would have to be versioned with it.
- **Walmart — no stated rationale.** *Inference:* a flat feed contract. The record's own measurement is the constraint: *"Shared values are shared by **repetition**, not reference"* — a seller transmits a complete item document per SKU and Walmart never hands the seller an id to point at, because there is no session in which to resolve one.
- **Google — no stated rationale.** *Inference:* Google receives feeds from merchants whose catalogues it does not host; there is no place for a shared row to live that both sides can address, so every value is a scalar and the only identity is the `contentLanguage ~ feedLabel ~ offerId` triple.
- **WooCommerce — the only explicit statement of the global-versus-local trade:** *"Attributes can be defined globally, so they’re easy to update across the entire store, and available to be used on any product, or; … defined individually, at the product level, and they will only exist for that single product."* (`11080.md:338`, `:629`; typographic apostrophe reproduced as the record has it — finding R2-6, the twin of R1-24)
- **commercetools — why values differ per type:** *"You wouldn't ask for the `Neckline` of a pair of jeans, would you? By defining appropriate Attribute types for each Product Type, you prevent irrelevant or nonsensical data from being entered, maintaining data integrity and simplifying product management."* (#11081 §3)
- **Magento — Adobe states the purpose of the set, not of the shared row:** *"The attribute set determines the fields that are available during data entry, and the values that appear to the customer."* (#11082 §1.2) *Inference for the row:* Magento fans the label out per `store_id`, so the label cannot be the identity — a store-view translation of "Green" must not create a second value. The integer option id is what makes localisation possible at all.
- **Shopee — no stated rationale.** *Inference:* a marketplace that wants a clean catalogue but cannot block a seller's listing, hence a shared `value_id` with `0` as an explicit "I am typing my own" sentinel.
- **Tokopedia (both eras) — operational statements only:** *"Use the Get Attributes to check what attributes are mandatory and pass attribute values via the Create Product…"* (#11048 §1.8). *Inference:* the same marketplace constraint as Shopee, and the same answer — built-in ids with a seller-typed escape.
- **Salesforce B2C — no stated rationale in the record for the value shape.** *Inference:* a single-tenant storefront where the merchant authors both the attribute and its values, so nothing forces a decision either way.
- **GS1 and BPOM are not platforms and are not tallied**, but they carry the only *stated* rationale for a typed quantity: GS1 defines `netContent` as a `QuantitativeValue` because a measurement without a `unitCode` is not interpretable across trading partners, and BPOM/Kemendag make the printed unit a function of the magnitude (§6.3). Both are quoted in §6.3 and in `sources-and-corrections.md`.

### 6 · Cleanest / structurally correct for us

The platforms split on all three questions, so this is a full design pass; the sketch is `design-A4.md`.

#### 6.1 Value shape — what each costs against our tables

**(a) free string + normalisation on write (#10778 V6).** One `save()` hook. It fixes **1.6%** of the duplication (5,580 → 5,489) and leaves the 16 spellings of `PT UNILEVER INDONESIA TBK`. It is irreversible (the original spellings are gone). It cannot give ordering, cannot give a rename, and cannot make the variant key a database constraint. It is the only option that requires no new table, and that is its whole case.

**(b)/(c) option row.** `ProductAttributeOption(attribute_id, code, label_en, label_id, display_order, amount, unit)` plus a `value_option` column and an `option` entry in `TYPE_CHOICES`. `_get_value`/`_set_value` need no edit because they already dispatch on `"value_%s" % attribute.type`. The read API and both frontend renderers keep working if `_option_as_text` returns the localised label — the hook is already looked up at `models.py:775-776`. **The write path is the real change**: `value` on the wire must become an option id, which touches `staff_serializers.py:38`, `product-attribute.model.ts:21` and the formly type map. Resolving by label instead would work without an API change and would silently re-point values on a rename — which defeats the purpose of having a row.
**Store a real FK, not a code — Akeneo is the cautionary case and it is the closest analog to what we would build.** It has genuine option rows, but the *product* stores the option **code** as a string inside `raw_values` JSON, so *"**Referential integrity is a validator, not a foreign key**"* — and the validator has to compare case-insensitively: `if (!in_array(strtolower($value->getData()), …))` (#11069 §1.5). A code-copy buys the row's curation surface and hands back the row's guarantee. Our `ProductAttributeValue` already has one column per type, so `value_option_id` as a real FK costs exactly what `value_text` costs and keeps the guarantee.
The problem (b)/(c) causes: **one list has to hold every category's values.** Our own `Rasa` would carry both Soto and Cokelat. The industry's answer to that is a second type, not a subsetted list (§A3).
`label_en`/`label_id` is not invention on either side. In our own repo, `Category` already stores exactly that pair (`models.py:110-121`) and serialises it (`api/apicategory/serializers.py:8-19`); adopting it removes the attribute display names from the frontend translation bundle, which is where they have already drifted (`internalname`). And it is the shape two of the platforms ship: Magento splits the option into `eav_attribute_option` (the identity) and `eav_attribute_option_value` (the label, `UNIQUE (store_id, option_id)`), and Salesforce splits the value into `@value` (required, the code — `red`, `1 GB`) and `<display-value>` (a localized string, 0..N). **A code plus per-locale labels is the industry's answer to the same problem we have.**

**Shopify's linked-versus-unlinked split is the same trade, run in production at scale.** An *unlinked* value is a `ProductOptionValue` row scoped to one product with `linkedMetafieldValue: null`; a *linked* value carries a `gid://shopify/Metaobject/<n>` that many products point at. Shopify's own words for why: *"Instead of using simple text for option values, you reference metaobjects that contain structured data. For example, instead of a color option with the text value "Red", you reference a metaobject that includes the color name, hex code, and taxonomy references… The metaobject's display name becomes what customers see, while the structured data powers features like improved search and marketplace integration."* And the payoff, stated by the vendor in the plainest possible terms: *"you can edit the color `black` to be `graphite` and your variant values are updated anywhere that color is used."* **That is the rename argument for a shared row, made by the platform that started with strings.**

**Judgement: (c) is not a compromise, it is the shape the existing model was written for.** `manufacturer` stays `text` on day one and becomes `option` later by a data migration, with nothing else branching on the choice.

#### 6.2 Where the list lives

**(A) on the attribute** is the only location that supports a cross-category filter, a single rename and a single ordering. **The filter is not hypothetical — Square ships the query.** `CatalogQueryItemVariationsForItemOptionValues.item_option_value_ids` returns *"All ItemVariations that…"* match a set of option-value ids, across items; the record calls that *"what makes the row global"* (#11049 §1.4). That is the A0↔A4 coupling answered from the other end: **a filter over values is a join over rows, and it has no formulation over copied strings that survives a rename or a spelling.** It is what Akeneo, Magento and the Shopify taxonomy do; measured in the corpus, a `TaxonomyValue` belongs to **exactly one** attribute (0 of 74,820 shared) and the category→attribute edge carries no value list.
**(B) on the category** needs a fourth table and creates a second place a value can be wrong (a product holding an option its category no longer offers). Nobody ships pure (B).
**(C) on the family** is Shopify's shape, and the collection measured it rather than assuming it: querying 600 products of Shopify's own demo shop through the public Admin-GraphQL proxy at `2026-07` returned **600 distinct `Product` ids, 600 distinct `ProductOption` ids and 600 distinct `ProductOptionValue` ids — for exactly one distinct option name (`Title`) and one distinct value name (`Default Title`)**. ⚠️ **Limit, stated (finding R1-21):** `Title` / `Default Title` is Shopify's synthetic default for a product with no merchant-authored options, so this shows the *default* value row is minted per product; it does **not** show that two products each carrying a merchant-authored `Red` get distinct ids. The schema argument beneath it does not depend on the shop's contents: Every option-value mutation takes `productId: ID!` non-null (`productOptionsCreate`, `productOptionUpdate`, `productOptionsDelete`). The value row really is minted per product.
It is the shape to reject as the home of *our* list: at 106,161 products, most of them families of one under Lock 2, the option table would be larger than the value table, no two families would share a value, and there would be nothing to filter, rename or order. **Shopify itself bolts the missing sharing back on** — that is what a *linked* option value is (§6.1 and §3). It is right as the home of a *selection* — which is D5's question, not A4's.

**A4↔A5 (FAMILY owns the level; I own the shape):** whatever level A5 puts a value on, **the shape must be identical on both levels**, or we buy two editors, two serializers and two filter paths. The matrix already names the schema fork — *"Either a nullable family column beside it with a check that exactly one is set, or a second table"* (`catalogue-decision-matrix-2026-09-16.txt:246`). Either is compatible with an option row on list-location (A); neither is compatible with a family-scoped list, because a member value and a family value would point into different vocabularies.

#### 6.3 Quantities, and the ordering question that hangs off them

**(ii) unit fixed on the definition is what we already ship** — the unit is just in `ts/assets/i18n/product/*.json` instead of a column. Moving it to a `unit` column on `ProductAttribute` completes the shape and removes a frontend release from the critical path.
It breaks when one attribute carries values in more than one unit, which is our case: `SOKLIN SOFTERGENT SAKURA STRAWBERRY` holds `215 GR · 720 GR · 1.44 KG · 2.7 KG` **and** a `700ML` refill.

**And Indonesian law makes it break by design.** Permendag No. 31/M-DAG/PER/10/2011 (Barang Dalam Keadaan Terbungkus), Pasal 7(3): *"**Penulisan lambang satuan harus disesuaikan dengan ukuran nilai kuantitas nominal BDKT** sebagaimana tercantum dalam Lampiran II"* — "the unit symbol must be matched to the magnitude of the package's nominal quantity". Lampiran II, reproduced whole in `corpus/bpom/` (read from the page image; the ministry PDF is a scan): weight `Qn < 1 g → mg`, `1 g ≤ Qn < 1000 g → g`, `1000 g ≤ Qn → kg`; liquid volume `Qn < 1000 mL → mL`, `1000 mL ≤ Qn → L`. **The printed unit is a function of the magnitude, fixed by regulation.** A unit fixed on the *definition* therefore cannot be correct for an attribute whose values span the 1,000-unit boundary — which is exactly `215 GR` versus `1.44 KG`. Shape (ii) is legally unavailable for net content in Indonesia.
PerBPOM No. 31 Tahun 2018 Pasal 26(2)–(3) fixes the unit *family* by product form as well: *"a. **ukuran berat untuk Pangan Olahan padat**… b. **ukuran volume untuk Pangan Olahan cair**… c. ukuran berat atau volume untuk Pangan Olahan semi padat atau kental"*, written as `mg/g/kg` for solids and `ml or mL / l or L` for liquids, with net content a mandatory label element (Pasal 5(1)(c)) and drained weight (`bobot tuntas`) additionally mandatory for anything in a liquid medium (Pasal 27(1)–(2)). Two official copies retrieved (BPK 627,263 B; Berita Negara 1452/2018 347,678 B); both amendments (PerBPOM 20/2021, 6/2024) leave Pasal 26 and 27 untouched (`grep -c "Pasal 26"/"Pasal 27"` = 0 in each amendment's extracted text).
**(iii) amount + unit on the value** handles that directly and is Akeneo's `metric` — collected at source: the *definition* carries `metric_family`, `default_metric_unit`, `decimals_allowed`, `negative_allowed` (`raw_Attribute.orm.yml:59-84`), while the *value* carries its own `{"amount": …, "unit": …}` (`Normalizer/Standard/Product/MetricNormalizer.php:24-46`, and real vendor payloads `{"amount": 98,"unit": "CENTIMETER"}`, `{"amount": "-20.5000","unit": "CELSIUS"}`). So Akeneo is (iii) **with (ii) as a default** — the unit is defaulted on the definition and overridable on the value. That is the shape our law requires, arrived at independently.
**GS1 models net content the same way and not as a label**: `gs1:netContent` has `rdfs:range gs1:QuantitativeValue`, and a `QuantitativeValue` is `gs1:value` (`xsd:float`) plus `gs1:unitCode` (`xsd:string`, *"a Measurement Unit from UN/ECE Recommendation 20 … e.g. GRM = gram"*) — `gs1Voc.ttl` v1.18, 1,270,763 B, confirmed against the v1.16 copy on GS1's GitHub. `netWeight`, `grossWeight` and `drainedWeight` have the same range; `drainedWeight` alone is domained to `gs1:FoodBeverageTobaccoProduct`.
**And net content is structurally a per-member value, not a family fact** — which is why its sortability is A4's problem and not a display detail. GS1's *GTIN Management Standard* R1.1 (Sep 2023) §2.3: *"**Any change (increase or decrease) to the legally-required declared net content that is printed on the pack, requires assignment of a new GTIN.**"* — quoted to the end of its clause, including the qualifier that follows two paragraphs later: *"Local, national or regional regulations may require more frequent GTIN changes. Such regulations have precedence over the rules provided within the GTIN Management Standard."* The GS1 *General Specifications* R26.0 §4.2.2.2 words the same obligation more weakly (*"will **usually** lead to a change in the Global Trade Item Number"*); both are recorded as they stand. Our own data agrees: the four `SOKLIN SOFTERGENT SAKURA STRAWBERRY` sizes carry four distinct 13-digit GS1 barcodes (`8998866612180`, `8998866612173`, `8998866612166`, `8998866622493` — `sql/results/matrix-examples-recheck.csv`). So each net-content value sits on its own sellable row, the picker that chooses between them is a real picker, and the order it shows them in is the question §6.3 is answering.

**(iv) the label is the record, the magnitude is derived on write** does the same thing without asking staff to type two fields: staff type `1.44 KG`, a write-time parse stores `amount = 1440, unit_canonical = 'g'`. Measured: **all 886 labels parse; 0 fail** (`sql/quantity-vocabulary.sql`).
**Note how the regulation and this shape agree.** Lampiran II defines the printed unit as a *function of the magnitude* — so once the magnitude is stored in a canonical base unit, the legally correct display unit is derivable, not a second fact. Storing the magnitude therefore loses nothing that the label carried and gains the order; keeping the label as the record preserves the supplier's exact printed form, which is what the shelf and the pack actually show.

#### 6.4 The variant key

With free strings the key is a tuple of `value_text` and is only as stable as the text — `Ayam bawang` and `Ayam Bawang` are two members of one family and the database cannot tell. With option rows the key is a tuple of integer FKs and `UNIQUE (group_id, option_a_id, option_b_id, option_c_id)` is an ordinary composite index. **D7's default ("both at write, in the DB") and lock condition 4's composite-FK mirror are reachable only under value shape (b) or (c).** ~~The matrix says the same from the other end~~ — **corrected (finding R1-6): that sentence is the card's, not the matrix's.** *"Ordering, rename and a stable variant key come only with (a) or (c)"* is `evidence/pages/catalogue-next-steps-v7.txt:269` — the same page this brief is answering, so it restates the question rather than corroborating the answer. The matrix's own D8 options line reads differently and does **not** mention the variant key: *"Ordering, rename and **normalisation** come **free** only with (a) or (c)"* (`catalogue-decision-matrix-2026-09-16.txt:2153`). The variant-key claim therefore rests on the design argument above, not on a second source.

#### 6.5 The fork↔A4 consequence (TREE states the taxonomy facts; this is the consequence)

The published Shopify taxonomy can express **only closed choice lists** — no attribute in either distribution file carries a `type`, a `unit` or a `position`, and none has an empty value list (§5). Three consequences for the value model, and they are mine, not TREE's:

1. **Adopting the taxonomy pre-decides D8 as "shared option row, list on the attribute" (shape (b)/(c), location (A))** — because a taxonomy attribute *is* a closed list of identified values, and adopting it without option rows would mean importing 74,820 values as strings and discarding their ids.
2. **It does not decide D9, it removes the question's answer.** The taxonomy has no net-content or size attribute; 329 size/weight/volume names exist and 219 are single-category. Meanwhile net content is the single most-needed kind in our own tree — **617 of 1,686 nodes (36.6%)**, ahead of colour (494) and flavour (199) (`briefs/TREE/node-attribute-need.md` §1). **So the one attribute we need most is the one the taxonomy does not have, and we would have to author it ourselves, with our own quantity shape, on top of an adopted tree.** The matrix reached the same conclusion from the tree side: *"Our biggest axis … is not in the standard and would not be solved by adopting it. D9 stays ours either way."*
3. **A closed list cannot hold our flavours as published.** Shopify's global `Flavor` list is 30 values; **0 of the 73 word tokens in our 43 Indomie flavour phrases appear in it** (`corpus-analysis/indomie_vs_shopify_flavor.out`). Adopting the taxonomy means adopting its value ids *and* extending every list we actually use — i.e. the closed list becomes ours to curate anyway, which is the (a)-plus-more-types pattern from §A3, imported rather than authored.

### 7 · Recommendation

**Judgement (mine): value shape (c) hybrid by type; list location (A) on the attribute; quantity shape (iv) — the label is the stored record and the magnitude is derived on write.** Confidence: **medium-high** on (c)+(A); **medium-high** on (iv) over (iii); **high** that shape (a)-only (string + normalisation) is insufficient. ~~high on (c)+(A)~~ — **reviewed and lowered (findings R1-4, R2-1).** The option's headline cheapness was overstated: reason 1 grew from “a two-line change” to one table, one column, one enum entry, one validator method, one type-alias member, one API field, one formly type and `_option_as_text`. The **high** on (a)-only being insufficient is unmoved: it rests on measured duplication (16 spellings of one manufacturer over 1,108 rows) that no round touched.

1. **The model's read path already implements (c), and its write path needs one method.** A seventh typed column costs no change to `_get_value` (`models.py:749-751`) or `value_as_text` (`:775-776`), and the invariant is clean today (471,143 rows, every one with exactly one populated column matching its type). 2. **(a) does not fix what it claims to fix.** Normalisation reaches 1.6%; the measured duplication is 16 Unilevers and 10 Mandoms, which needs rows plus a merge tool.
3. **The junk is concentrated, so rows make it cheap.** 31 distinct letterless values cover 15,516 rows (33%). As rows, that is 31 deletions and a re-point, not a 15,516-row `UPDATE`.
4. **Ordering, rename and a database-enforceable variant key exist only with rows.** That is not a preference, it is a constraint statement (§6.4).
5. **The derived magnitude is measurably free and measurably necessary**: 0 curation against 886 hand-set positions, and right on the 782 families text order gets wrong.

#### The conflict the errata names, resolved

> #10778 **V4**: *"An axis value is a SINGLE TEXT LABEL — `"200 ml"`, not `{200, "ml"}`. … The only argument for splitting is ordering, and it fails: every surveyed system hand-orders picker values with a position column … **Nobody drives a picker from a stored quantity** … **Splitting forfeits nothing** — unit pricing, range faceting, conversion and `500 g ≡ 0.5 kg` are unavailable from the axis value in *every* system surveyed **including the two-field ones**; those belong to #10942."* (`10778.md:128`)
> The matrix **D9**: *"Four members of one size axis, in two different units. **They do not contradict each other on any fact. They describe two different mechanisms and neither source says which one we would pay for.** V4 is about *how a picker can be ordered* (a hand-set position column, which does make a label sortable). D9 is about *what a label does by itself* (nothing — it has no magnitude, so any default order is wrong). Both statements are true. **Resolution, measured:**

- **V4's core claim — CONFIRMED and kept.** An axis value is a single text label. `1.44 KG` and `215 GR` are what staff type and what the page must print; splitting the label into `{1.44, "KG"}` would force staff to enter two fields and would lose the printed form (`700ML` vs `700 ML`). Our own data agrees that the label is the record: the `IMPLORA` family's shade labels are already the identity of the members.

Hand-ordering costs **886 labels** catalogue-wide (**399** inside real families) and a re-number on every insertion. A derived magnitude costs **0** and is correct on 100% of the 886. V4 compared mechanisms; it never compared their price.
